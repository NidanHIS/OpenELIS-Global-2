# Design: OCL import must not overwrite lab-owned configuration

Generated by /office-hours on 2026-08-18 Branch: dev (fix lands in
OpenELIS-Global-2 @ nidan-dev) Repo: NidanHIS/nidan-docker (code:
NidanHIS/OpenELIS-Global-2) Status: APPROVED Mode: Startup (intrapreneurship)

## Problem Statement

After an unclean shutdown at Bijaynagar hospital, panel membership in OpenELIS
reverts to the values shipped in the OCL package. Tests the lab added to a panel
disappear, tests they removed come back, and manual ordering is lost.

Root cause is two defects stacked:

1. `OclConfigurationHandler.mapLabsetPannels()` (:197-225) calls
   `panelItemService.updatePanelItems()` (:219), which does `deleteAll` then
   reinsert from the zip. It runs unconditionally, with no diff. Confirmed from
   container logs: a boot that processed zero concepts still rewrote all 16
   panels, and `panel_item` ids came out contiguous 264-359.
2. The only thing gating that import is a SHA-256 in
   `/var/lib/openelis-global/configuration/backend/ocl-checksums.properties`,
   written by `ConfigurationInitializationService.saveChecksums()` (:291) with a
   plain `FileWriter`, no fsync, no atomic rename, once per domain at the very
   end of the domain load (:154).

Three crash windows all land in the same place, checksum absent or empty on next
boot, full re-import, panels rewritten:

- power loss during the import (widest window, the import is not atomic with the
  marker)
- power loss between import completion and the file write
- power loss inside the ext4 writeback window after the write, which leaves a
  zero-length file

A third defect shares the root cause and has not been noticed yet:
`OclToOpenElisMapper` (:498-578) force-syncs test section, LOINC, unit of
measure and `is_active` on every existing test on every run. A lab moving a test
to a different department in the UI gets it reverted by the same event.

## Status Quo

Clean restarts are already safe. Verified on the local stack: deleted
`panel_item` 345 from CBC, ran `docker restart nidan-openelis`, log printed
`ocl configuration TTH_Laboratory_... unchanged (checksum matches). Skipping.`,
and the row stayed deleted. The failure needs an unclean shutdown or a lost
checksum file. That is why it does not reproduce locally on demand.

Today the workaround is manual: after every outage, someone re-enters the lab's
panel configuration through Panel-Test Assign, assuming they notice.

## Target User

Lab technicians and the lab admin at Bijaynagar hospital, plus every future
OpenELIS deployment that ships an OCL package. They configure panels once during
commissioning and expect that configuration to be permanent. They have no way to
tell that a power cut changed their test catalog.

## Constraints

- Live hospital database with real patient data. No cleanup-style migrations.
- OpenELIS runs Liquibase before the Hibernate SessionFactory exists
  (`HibernateConfig.java:26` is `@DependsOn("liquibase")`), so the import itself
  cannot move into a Liquibase changeset. It needs `TestAddService`,
  `PanelService`, `PanelItemService`, `LocalizationService`, none of which exist
  at changeset time.
- No `customChange` precedent in the repo. Every file under `liquibase/nidan/`
  is plain SQL.
- Deployment is `trigonaltechnology/openelis-global-2:latest` restarted by
  compose. Any schema change ships through the existing Liquibase changelog.

## Premises

1. The symptom is `updatePanelItems`, not the checksum. The checksum only
   decides whether the destructive code runs.
2. A clean restart is already safe. Verified by controlled test, not inferred.
3. Making the checksum file durable (fsync plus atomic rename) narrows the
   window but does not close it. Power loss during the import leaves the DB
   mutated with no marker. For the `ocl` domain, which has exactly one zip, the
   per-file-save half is a no-op.
4. Guarding only `mapLabsetPannels` fixes the reported symptom and does not
   regress first install, because panels are created with zero items in the same
   run.
5. Panels are not the only lab-owned data being reverted. Test section, LOINC,
   UOM and `is_active` are force-synced on every run.
6. The marker was not removed carelessly. `OclInnitializerTest.java:49` notes
   "marker file logic removed"; upstream `749de1d6a` generalized a per-import
   marker into this checksum framework. Adding a data-level guard operates at a
   different layer and does not fight that change.

## Approaches Considered

### Approach A: Panel guard only

`if (!panelItems.isEmpty()) continue;` in `mapLabsetPannels`. Effort S, risk
low. Rejected: leaves the test section, LOINC and UOM reversion live, which is
the same bug in a different table and the next unexplained incident.

### Approach B: Seed-only guards on both destructive paths

A, plus stop the test upsert overwriting section, LOINC and UOM on tests that
already exist, plus the fsync hardening. Effort M, risk low to medium. Rejected
by the user: both A and B permanently give up the ability for an OCL package to
push a genuine update.

### Approach C: Provenance flag plus DB import marker (CHOSEN)

Mark rows as OCL-managed or lab-edited; the importer only touches OCL-managed
rows, and a UI save flips a row to lab-owned. Move the ran-already marker into
the database, written in the same unit of work as the data. Effort L, risk
medium.

## Recommended Approach

Approach C, chosen by the user over the recommended B. The reasoning that
carries it: A and B both fix the bug by making the importer permanently unable
to update anything, which means every future OCL package revision becomes a
manual re-seed. C is the only option that keeps OCL useful as an upgrade channel
while making a human edit un-overwritable.

Prior art is `noupdate="1"` plus `ir.model.data` external IDs in Odoo, which
this team ships daily. OCL already supplies the external ID half (`guid` on
`test` and `panel`). The missing half is the do-not-overwrite flag.

### Part 1: Provenance flag

- Liquibase changesets adding a provenance column to `clinlims.panel_item` and
  `clinlims.test`. Values: `OCL` (created by import, import may update) and
  `USER` (touched by a human, import must skip).
- Import writes new rows as `OCL`.
- Every UI write path flips affected rows to `USER`:
  `PanelTestAssignController:144`, `PanelTestAssignRestController:152`, and the
  test admin controllers.
- `mapLabsetPannels` and the test upsert skip any row marked `USER`.
- Keep a small allowlist of fields OCL always syncs regardless of provenance.
  `is_active` / `retired` belongs there: a test retired upstream should still
  retire locally. Section, LOINC and UOM do not.

### Part 2: Import marker in the database

- Replace `ocl-checksums.properties` for the `ocl` domain with a row recording
  domain, file name, checksum and timestamp.
- Written through the same connection as the import work, so a crash cannot
  leave data without a marker or a marker without data.

### Migration decision (the crux)

Backfill every existing `panel_item` and `test` row as `USER`, not `OCL`.
Bijaynagar has already been customized, and there is no way to tell which rows
are original. Defaulting to `OCL` would let the first import after the upgrade
wipe them one final time. Defaulting to `USER` freezes the current state, which
is the correct failure direction for a live hospital. Rows created by imports
after the migration get `OCL` and stay updatable.

## Open Questions

1. **Transaction scope for Part 2.** The import is not currently one
   transaction. `testAddService.addTests` and
   `panelItemService.updatePanelItems` are each `@Transactional` on their own.
   True atomicity means wrapping ~269 concepts in a single transaction, which is
   a long-running write on a live DB. If we do not wrap it, the DB marker is
   still strictly better than the file (it survives power loss once committed)
   but the mid-import window stays open. Decide: wrap, or accept the narrower
   window and rely on Part 1 to make a re-import harmless. Note that if Part 1
   is correct, a re-import is no longer destructive, which weakens the case for
   the expensive wrapping. Part 1 may make Part 2 optional.
2. **Provenance granularity on `test`.** A per-row flag means one UI edit to
   LOINC also freezes the section. Per-field provenance is more correct and much
   more code. Recommend per-row plus the always-sync allowlist, and revisit only
   if it bites.
3. **Escape hatch.** Admins need a way to force a re-seed of a panel from OCL.
   Simplest is flipping the row back to `OCL` from the admin UI. Needs a design
   decision on where that lives.

## Success Criteria

1. Booting with `ocl-checksums.properties` deleted or zero-length changes no
   `panel_item` row and no `test` section/LOINC/UOM that a human has touched.
2. Killing the JVM mid-import and restarting leaves the DB consistent and
   reverts nothing.
3. A new OCL package version can still add new tests and panels, and can still
   update rows never touched by a human.
4. Regression test in `OclInnitializerTest`: run `performOclImport` against
   `src/test/resources/ocl/oclLabCollection.zip`, mutate a panel and a test
   section, run the import again, assert both survive. The harness already
   drives a real zip through a live context, so this is an addition of roughly
   20 lines, not a new fixture.
5. `mvn spotless:apply` clean, per the OpenELIS pre-commit rule.

## Distribution Plan

Existing pipeline covers it. The change ships in
`trigonaltechnology/openelis-global-2:latest`; Liquibase runs the new changesets
on container start. One rollout note: Bijaynagar needs the migration applied
during a maintenance window, and the backfill should be verified
(`select provenance, count(*) from clinlims.panel_item group by 1`) before the
next restart.

## Dependencies

- Interacts with `backfill-panel-item-sort-order.xml` and the recent sort-order

- `PanelCreatedOrUpdatedEvent` fires from `updatePanelItems` and drives the Odoo

## What I noticed about how you think

- You asked "is this because of checksum getting deleted automatically?" before
  any investigation ran. The mechanism turned out to be a checksum that never
  became durable rather than one that got deleted, but you were in the right
  room from the first message.
- You led with "i can't replicate this on the local." That is the discriminating
  fact, and it is the one most people bury three paragraphs down. It is what
  made the durability angle obvious instead of a guess.
- "should we make changes on the code? or should we move this to liquibase
  instead?" You reached for the transactional layer rather than a patch.
  Liquibase turned out to be blocked by the `@DependsOn("liquibase")` ordering,
  but the instinct behind the question, put the marker where the data is, is
  exactly what Part 2 of the chosen design does.
- You took C over my recommended B. B was the cheaper correct answer for the bug
  in front of you; C is the answer for the bug plus every OCL package you ship
  after it. Picking the more expensive option because the cheap one closes a
  door is a scope judgment, not a preference.
